The HC-SR04 measures distance by timing how long it takes a sound pulse to travel to an object and bounce back. readDistanceCM() sends the standard trigger pulse, then uses pulseIn() with a timeout to read how long the echo pin stays high, and converts that into centimeters using the speed of sound. The timeout matters: without it, pulseIn() can block indefinitely if no echo ever returns, freezing the whole program.
For the buzzer behavior, I treated this as three zones rather than one continuous formula, since the task describes three distinct behaviors (slow beep, faster beep, continuous), not a single smooth curve:
Far away (above MAX_RANGE) the buzzer is silent, since beeping for "nothing nearby" would be noisy and unhelpful. In the middle zone, I use tone() for a short fixed-duration beep followed by a gap, and map() to scale that gap based on distance, closer objects get a shorter gap, which means faster beeping, while distant objects in range get a longer gap and slower beeping. This linear mapping is simple and predictable to tune; you could swap it for a non-linear curve (e.g. inverse square) if you want the urgency to ramp up more sharply near the close end. Once the object crosses CLOSE_RANGE, the buzzer switches from beeping to a continuous tone using tone() with no delay/noTone cycle, which reads as a constant alarm rather than rapid beeping.
One limitation worth flagging: this loop uses blocking delay() calls inside the beep logic, so the sensor is only re-read once per beep cycle rather than continuously. That's fine for a simple proximity alarm, but if you needed the system to stay responsive to other inputs at the same time (e.g. a button), you'd want to rewrite the timing using millis() instead of delay() so the loop never blocks.
